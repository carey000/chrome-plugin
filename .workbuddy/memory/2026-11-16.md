## 追加：无服务器多端同步（本地文件 + git）调研
- **交付**：在 `docs/notes-feature-research.md` 末尾追加 §10（仅文档，零代码改动）。用户问「能否把改动同步到 sql/db 文件再传 git，跨浏览器/电脑保证同一个源」。
- **结论**：能做，但链路必须是 `chrome.storage.local → 导出文本文件 → git → 另一端 pull → 导入 → 各自 storage.local`；不是「扩展自动写 db 文件」。git 保证版本历史与权威副本，不保证实时一致性；扩展不会感知 `git pull`。
- **纠错要点**：`storage.local` 本身就是本地持久化（10MB，卸载即清除），缺的是跨设备文件出口；扩展页无 fs API，不能静默写任意路径；SQLite `.db` 二进制无法 diff/merge，应导出 JSON/MD 文本；`chrome.alarms` 是每台浏览器本地注册，git 只搬提醒定义，导入后必须 `syncAlarms()` 重建。
- **三方案**：A 手动导出/导入 JSON + git（推荐，复用 `docs/newtab-feature-research.md` P0-1 的 Blob 下载 / FileReader 导入设计，零新增权限）；B `storage.sync`（自动但约 100KB / 单项 8KB，且需登录 Chrome Sync，只能同步设置）；C Native Messaging + 本地脚本 + git（可自动，但需 `nativeMessaging` 权限、Windows `HKCU\Software\Google\Chrome\NativeMessagingHosts\<name>` 注册表、固定扩展 ID（`allowed_origins` 禁通配符）、host→Chrome 单条 1MB 上限）。
- **官方核实**：`downloads` 的 `filename` 只能是相对下载目录路径（绝对路径 / `..` 会报错），`saveAs:true` 弹选择器；native messaging 的 host manifest 字段与消息上限。
- **不要直接 git LevelDB 目录**：`Local Extension Settings/<ext-id>/` 是 Chrome profile 内 LevelDB 多文件结构，按 profile 与扩展 ID 隔离、运行时锁定、跨浏览器 ID 不同（第三方资料，官方未逐字说明物理路径）。
- **数据口径**：单个 `notes.json` 全量覆盖 + 每条 `id`/`updatedAt`/`deleted`，冲突靠人工看 diff，**不做自动合并/CRDT**；图片同步会撑大 diff，建议单独文件或放弃。
- **不确定/待实测**：`showSaveFilePicker` 在 `chrome-extension://` 页面是否可用、句柄跨会话是否免重新授权；`saveAs` 能否选到 git 仓库路径；unpacked 扩展 ID 是否随路径变化、能否用 manifest `key` 固定；Blob 下载在 MV3 CSP 下是否可用。
- **待用户确认（新增 5 项）**：跨浏览器范围（Chromium 系 vs Firefox/Safari）、是否接受手动两步、仓库位置与明文隐私、两端同时改的口径、图片是否必须同步。

- **用户原话**：「chrome.storage.local 不行啊，富文本如果放两张截图，就爆了」。判断成立，且比 §10.2 原表述严重：超限是**写入立即失败**，不是变慢。
- **官方依据**：`QUOTA_BYTES 10485760`（Chrome 113 及更早 5MB），按 "the JSON stringification of every value plus every key's length" 计**所有 key 总量**；超限 "fail immediately and set runtime.lastError... or a rejected Promise"。dataURL base64 膨胀约 4/3（编码机制，非实测值），设单张 X MB 则两张 ≈2.67X MB，不编造 X。
- **文档修正**：`docs/notes-feature-research.md` 改 §4.1 图片行、§10.2 首行、§10.6 的 `notes-sync.js` 行与数据格式口径（共 4 处），追加 §10.10。代码仍零改动。
- **两方案**：A 加 `unlimitedStorage` 权限（代码零改动但需重载，大 base64 仍走全量 JSON 序列化、导出文件与 git 仓库膨胀，解除后上限官方未写明）；B 分层（文本/元数据 → `storage.local` 的 `nt_notes_*`，图片 Blob → IndexedDB，**零新增权限**，推荐，因为同时保住 `notes.json` 可 diff）。
- **富文本引用链路**：paste → `clipboardData.files[i]` Blob → `imgId` → IndexedDB `put` → HTML 只存 `<img data-note-img="<id>">`（不存 `blob:` URL 刷新失效、不存 `data:` URL 回到配额）→ 渲染时 `createObjectURL` + 卸载时 `revokeObjectURL`。改动面：新增 `newtab/note-images.js` 一个模块 put/get 两入口，`manifest.json` 不动。
- **git 影响**：`notes.json` 只放文本 + `imgId`；图片默认不进 git，跨端缺失显示占位；若必须同步图片则需逐张下载 / FSA 目录 / Native host / zip，且与「单文件导出」前提冲突。
- **不确定需实测**：扩展 origin 的 IndexedDB 是否适用 web.dev「单 origin 最多 60% 磁盘」（用 `navigator.storage.estimate()` 测）、卸载扩展是否清除 IndexedDB、MV3 CSP 是否放行 `blob:` 图片、`unlimitedStorage` 解除后上限、`crypto.subtle` 在扩展页可用性。
- **待用户定（新增 3 项）**：选 A/B、图片是否必须跨端、单张图片大小上限。

## Bug 定位：Figma 复制失效 / 右键变原生（已定位根因，未改动代码）
- **现象**：打开 figma.com 后复制失效、右键弹出浏览器原生菜单；禁用扩展后恢复。
- **根因**：`content/unclip-main.js`（解除复制限制，MAIN world、document_start、`<all_urls>`、all_frames）在 `document` 上以 capture 阶段注册 `copy/cut/contextmenu/selectstart/keydown/keyup` 的 blocker（L16、L36-38），命中时无条件 `event.stopImmediatePropagation()`（L25-34），抢在页面自身 handler 之前掐断事件。`enabled` 默认 `true`（L21），bridge 读不到开关时也按开启处理（`unclip-bridge.js` L18-20）。Figma 的右键菜单与复制依赖自己的 `contextmenu`/`copy`/`keydown` 监听器 + `preventDefault`；被掐断后无法 preventDefault → 浏览器走原生默认行为，且 Figma 内部剪贴板格式没写入 → 表现为复制失效。
- **附带因素**：`CSS_RULE` 全局 `user-select: text !important`（L18-19）也干扰依赖 `user-select:none` 的 Canvas UI。
- **关键机制**：`stopImmediatePropagation()` 阻止同节点后续所有监听器，但不阻止默认行为；代码注释 L32 的假设只对「网页禁止复制」场景成立，对「网页用这些事件实现自身功能」的富应用（Figma/Miro/在线文档）是误伤。
- **修复方向待用户选**：① unclip-main 内加域名白名单/黑名单；② 收窄 EVENTS（去掉 contextmenu / keydown）；③ 把 unclip 从全局注入改为只对目标站点启用（config.match 不再恒 true + main 层同步判断）。本轮只做静态源码核对，未实机验证。
